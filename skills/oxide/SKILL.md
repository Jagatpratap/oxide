# Oxide

Oxide is a game engine and editor modelled on Unity. Scenes hold GameObjects with a Transform
hierarchy and Components; game code is Rust instead of C#. If you know Unity, most names carry
over: `Start`/`Update` become `start`/`update`, `GetComponent<T>()` becomes
`ctx.get_component::<T>()`, `Debug.Log` becomes `debug_log!`.

There are two ways to work on an Oxide project, and you usually need both:

1. **Edit files**: write Rust scripts in `Scripts/src/`. The editor recompiles and hot-reloads
   them when a file is saved.
2. **Drive the running editor over MCP**: create objects, add components, set fields, make
   materials and prefabs, enter Play mode, read the Console and take screenshots. Prefer this
   to hand-editing scene, prefab or `.meta` files.

## Project layout

```text
MyGame/
  Assets/                  scenes (.scene), prefabs, models, materials (.mat), textures, audio
  Scripts/                 the game's Rust crate (a dylib named after the project)
    src/lib.rs             lists every script in the oxide::scripts! macro
    src/*.rs               one file per component, usually
    Cargo.toml             add crates.io dependencies here
  Packages/                packages embedded in the project (Package Manager)
  ProjectSettings/         *.yaml settings and ProjectVersion.txt (the editor version)
  AGENTS.md                notes for AI agents; yours to edit
  Library/                 generated, never edit or commit
  Cargo.toml, .cargo/, rust-toolchain.toml   generated by Oxide on every open, don't edit
```

Scenes, prefabs and `.mat` files are YAML and can be read to understand a project. Change them
through the editor (MCP tools) when it is running, because it holds the open scene in memory and
will overwrite your edit on the next save.

## Writing a script

```rust
// Scripts/src/mover.rs
use oxide::prelude::*;

#[derive(Clone, Default, Reflect)]
pub struct Mover {
    /// Metres per second. Doc comments become Inspector tooltips.
    #[reflect(range(0, 20))]
    pub speed: f32,
    pub target: Option<GameObjectId>,   // a scene object, set by drag and drop
    pub bullet: Option<Prefab>,         // a prefab asset
}

impl Component for Mover {
    fn start(&mut self, ctx: &mut Ctx) {
        debug_log!("Mover started on {}", ctx.name());
    }

    fn update(&mut self, ctx: &mut Ctx) {
        let input = ctx.input();
        let dir = Vector3::new(input.get_axis("Horizontal"), 0.0, input.get_axis("Vertical"));
        let step = dir * self.speed * ctx.delta_time();
        ctx.transform().translate(step);
    }
}
```

Then register it in `Scripts/src/lib.rs`; a script that isn't listed doesn't exist for the
editor:

```rust
mod mover;
pub use mover::Mover;

oxide::scripts! {
    Mover => "Scripts/Mover";   // type => Add Component menu path
}
```

Rules that trip people up:

- Components must be `#[derive(Clone, Default, Reflect)]` (or `Clone` + `Reflect` with a manual
  `Default`). Public fields show in the Inspector and are saved with the scene; mark a field
  `#[reflect(skip)]` to hide it.
- Field types the Inspector understands: numbers, `bool`, `String`, `Vector2/3/4`, `Quaternion`,
  `Color`, enums deriving `Reflect`, `Option<T>`, `Vec<T>`, nested `Reflect` structs, asset handles
  (`Handle<Material>`, `Handle<AudioClip>`, ...), `GameObjectId` and `Prefab`.
- Unity messages are trait methods on `Component`: `awake`, `on_enable`, `start`,
  `fixed_update`, `update`, `late_update`, `on_disable`, `on_destroy`,
  `on_collision_enter/stay/exit(ctx, &Collision)`, `on_trigger_enter/stay/exit(ctx, other)`,
  `on_message` (for `invoke` and `send_message`), `on_draw_gizmos`.
- Space is left-handed, +Y up, +Z forward, angles in degrees, colours sRGB 0 to 1.
- Don't edit `rust-toolchain.toml`: scripts must use the exact compiler the editor was built
  with. Add other crates to `Scripts/Cargo.toml` as usual.

Common calls (all on `ctx`):

| Unity | Oxide |
|---|---|
| `transform.position`, `Translate`, `Rotate`, `LookAt` | `ctx.transform().position()`, `.set_position(v)`, `.translate(v)`, `.rotate(euler)`, `.look_at(p)`; another object: `ctx.transform_of(id)` |
| `GetComponent<T>()` | `ctx.get_component::<T>()`, `ctx.get_component_mut::<T>()`, `ctx.world.get_component::<T>(id)` |
| `Instantiate(prefab, pos, rot)` | `ctx.instantiate_prefab(&prefab)` (a `Prefab` or an asset path), `ctx.instantiate_prefab_at(...)` |
| `Destroy(obj)`, `Destroy(obj, t)` | `ctx.destroy(id)`, `ctx.destroy_after(id, t)`, `ctx.destroy_self()` |
| `GameObject.Find`, `FindWithTag`, `FindObjectsByType` | `ctx.find(name)`, `ctx.find_with_tag(tag)`, `ctx.find_objects_by_type::<T>()` |
| `Input.GetAxis`, `GetKeyDown`, `GetButtonDown` | `ctx.input().get_axis("Horizontal")`, `get_key_down(KeyCode::Space)`, `get_button_down("Jump")` |
| `Physics.Raycast` | `ctx.physics().raycast(origin, dir, max_distance, layer_mask)` |
| `StartCoroutine` | `ctx.start_coroutine(\|co\| async move { co.wait_for_seconds(1.0).await; })` |
| `Invoke`, `InvokeRepeating` | `ctx.invoke("Fire", 2.0)`, `ctx.invoke_repeating(...)` (delivered to `on_message`) |
| `SendMessage` | `ctx.send_message(...)`, `ctx.broadcast_message(...)` |
| `SceneManager.LoadScene` | `ctx.load_scene("Level2")`, `ctx.load_scene_async(...)` |
| `Debug.Log/LogWarning/LogError` | `debug_log!`, `debug_log_warning!`, `debug_log_error!` |
| `Time.deltaTime`, `Time.time` | `ctx.delta_time()`, `ctx.time().time()` |

When unsure of a signature, read the engine source: in a release install it sits next to the
editor (the folder holding `crates/`), and `Cargo.toml` at the project root shows its path on the
`oxide = { package = "oxide_dylib", path = ... }` line. `crates/oxide_scene/src/ctx.rs` has
every `ctx` method.

The `oxide::scripts!` macro also takes sections after a `;` for other kinds of code:
`editors:` (custom Inspectors), `assets:` (data assets, Unity's ScriptableObjects),
`behaviours:` (Animator state machine behaviours), `playables:`, `pipelines:`, `tests:`
(play-mode tests) and `extensions:` (editor windows, menu items, tools, overlays). See
`references/getting-started.md`.

## Checking your work

After saving a script, the editor recompiles in the background (usually under a second). Then:

1. Call `get_console_logs` with `min_type: "Warning"`. Compile errors appear there with file and
   line, and the old code keeps running until the errors are fixed.
2. Call `list_component_types` to confirm the new component is registered, then
   `add_component` it to an object.
3. `editor_play` to enter Play mode, `step_frames` or wait, then `inspect_object`,
   `get_console_logs` and `capture_screenshot` to see what happened. Leave Play mode with
   `editor_play` again; Play-mode changes are thrown away, like Unity.

For Rust-level checks without the editor, run `cargo check -p scripts` (or `cargo test -p
scripts` for Edit-mode tests) in the project folder.

## Driving the editor over MCP

The editor serves MCP while it is open. The project's `.mcp.json` (Claude Code),
`.cursor/mcp.json` (Cursor) and `.vscode/mcp.json` (VS Code) point at it; each project gets its
own port, so two open projects never mix up. If the tools aren't available, the editor isn't
running: ask the user to open the project from the Oxide Hub (or run `oxide open <folder>`).

Typical flow:

1. `get_engine_info` and `editor_get_state`: which project and scene is open, Edit or Play mode,
   what's selected.
2. `get_hierarchy`, then `inspect_object` for details. Objects are named by id, name or a
   `"Parent/Child"` path.
3. Change things with `create_object`, `add_component`, `set_component`, `set_object`,
   `create_material`, `create_prefab`, `instantiate_prefab`, `import_model`. Each change is one
   Undo step (`editor_undo` reverts it).
4. Look at the result with `capture_screenshot` (pass `camera_position` and `look_at` for any
   viewpoint) and check `get_console_logs`.
5. `save_scene` when the user wants the change kept.

Specialised tools cover terrain, navmesh, animation, timeline, particles and VFX, UI, audio,
localization, packages, project settings, the profiler and more. The full list with arguments
is in `references/mcp.md`; `tools/list` on the server is the live source.

Ask before destructive calls (`destroy_object`, `new_scene`, `load_scene`, `apply_prefab`,
`quit`) unless the user already asked for that change.
